# layout 원본 → 격자 — 엔진 작업자에게

2026-09-11 사용자 결정: 맵 제작자는 그림과 함께 `layout.json`에 다섯 가지 배치를 적는다. 아스키를 편집 원본으로 삼지 않는다. 엔진의 `from_layout`이 격자를 생성하고, `town.json`은 layout을 참조하는 방향이다. 기존 장면·게이트용 `from_ascii`는 유지한다.

## 이번 작업 범위

- `layout.json`을 명시 배치 형식으로 갱신했다.
- 루트 `town_layout.py`에 엔진을 import하지 않는 `compile_layout(layout)`을 준비했다. 엔진의 `from_layout`에서 재사용할 수 있다.
- `to_ascii.py`는 이 함수를 불러 검토용 결과를 출력한다. 기존의 건물 높이 추측·소품 앵커 1칸·NPC 픽셀에서 칸 추정 규칙은 제거했다.
- 미리보기는 동일 layout의 막힌 칸·문턱·출발·진입점·NPC를 겹쳐 보여준다. NPC와 기존 모험가의 그림 발 위치도 칸 중심에서 계산한다.
- 보호 요청에 따라 `dungeon_gm.py`, `composed_actions.py`, `brains.py`는 변경하지 않았다. `from_layout`, 러너의 참조 해석, `check_town.py`의 layout 직접 입력 지원은 엔진 작업에서 연결해야 한다.
- 현행 `town.json`은 교체하지 않았다. 기존 `check_town.py`로 생성 후보를 검사하면 새 NPC 정의 3개가 없어서 실패한다. 이름 대신 id를 숨겨 이 검사를 우회하지 않았다.

## 좌표 계약

`schema: "town-layout-v1"`, `size: [25,18]`, `tileSize: 48`, `border: 1`.

모든 저작 칸 좌표는 **외곽벽을 제외한 내부 맵의 0-based [x,y]**다. 왼쪽 위가 [0,0]. 사각형은 [x,y,width,height]이고 끝 좌표를 포함하는 표기가 아니다. 예: [6,5,13,6]은 x=6~18, y=5~10을 막는다.

엔진 격자를 만들 때 사방에 `border`만큼 벽을 추가한다. 따라서 이번 출력은 27×20, 모든 배치 좌표는 두 축에 +1이다. 이 이동을 한 번만 적용한다. 그림 레이어가 엔진 좌표계를 사용하면 `visual.offset: [1,1]`을 사용한다.

NPC·모험가의 그림 발 위치(px)는 `(cell + 0.5) * tileSize`다. 픽셀 x/y를 별도로 작성하지 않는다. 건물·소품의 그림 앵커는 시각 정보이고, 충돌은 아래 명시된 사각형이 정한다.

| 필드 | 형식 | 의미 |
|---|---|---|
| `blocked_rects` | `[{id, rect:[x,y,w,h]}]` | 막힌 영역. 사각형끼리 겹쳐도 된다. |
| `entrances` | `[{id, cell:[x,y], kind:"threshold" 또는 "door"}]` | 마지막에 열어 주는 출입구. 문턱은 `.`, 양쪽 통로가 있는 실제 문은 `+`. |
| `starts` | `{"1":[x,y], "2":[x,y], "3":[x,y]}` | 출발 칸. 이번 첫 버전은 3개 이상, 1 포함. |
| `dungeon_entry` | `{cell:[x,y], placeholder:true, note:...}` | 정확히 하나인 `>` 위치. 이번에는 샛길 남쪽 임시 진입점. |
| `npcs` | `[{id, cell:[x,y], row:외형행}]` | NPC 정의 id와 위치. row는 표시 전용. |

`dungeon_entry.placeholder`는 이번 장소가 별도 던전 입구 구역 완성 전의 임시 연결임을 알리는 저작 정보다. 원래 확정한 여섯 구역 구성을 폐기한 것이 아니다.

## 변환 순서

1. size 범위를 바닥으로 채우고 blocked_rects를 벽으로 칠한다.
2. entrances의 칸을 명시적으로 연다. 문턱은 막힌 건물 앞면의 홈이며 실내 포탈 기능은 아직 없다.
3. 던전 진입점, 출발점, NPC를 배치한다. 벽이나 다른 배치에 겹치면 오류다. NPC id 중복도 오류다.
4. 첫 출발점에서 다른 출발점·모든 NPC·모든 출입구·던전 진입점까지 연결되어 있는지 확인한다.
5. 외곽벽을 두르고 모든 배치 좌표에 border를 더한다.

그림을 보고 벽을 추측하거나 NPC를 가까운 빈 칸으로 자동 이동시키지 않는다. 잘못된 배치는 오류로 되돌린다. 같은 파일에 있다고 그림과 사각형이 자동으로 일치하는 것은 아니므로 미리보기의 붉은 충돌 오버레이로 확인한다.

| 길드 문턱 | [12,10] | [13,11] |
| 출발 1 | [11,13] | [12,14] |

탁자와 의자는 샛길 남단을 가리지 않도록 왼쪽 빈터로 옮겼다. 울타리·게시판·벤치·탁자는 여러 칸의 발자국을 사용한다. 지붕 전체를 벽으로 처리하지 않는다.

## from_layout 연결 제안

엔진 작업에서 `compile_layout(layout)`의 반환 `map`을 기존 `from_ascii` 초기화에 전달하면, 엔진 초기화 코드를 복제하지 않고 같은 판정을 사용할 수 있다. 반환 `npcs`는 엔티티 정의와 합치는 기존 러너 경로로 전달하고, 출발 좌표는 이미 border가 적용된 값이다. 구체적인 엔진 메서드 반환형은 기존 호출부와 맞춰 결정한다.

`town-layout-ref.json`은 향후 로더용 예시 `{"layout":"layout.json"}`이다. 상대 경로는 **참조한 town 파일의 디렉터리 기준**으로 해석한다. 저장소 루트의 town.json에서 참조하면 `art/town-v1/layout.json`이 된다. 현재 로더가 이 참조를 지원한다고 가정하지 않는다.

## 검증과 남은 연결

```powershell
python art/town-v1/to_ascii.py
python art/town-v1/verify_layout.py
python check_town.py art/town-v1/town-candidate.json
node art/town-v1/verify.mjs
```

첫 번째는 아스키·후보 JSON 생성, 두 번째는 잘못된 배치 거절 및 실제 `from_ascii`의 벽·좌표·경로와 대조, 세 번째는 현행 정식 검사, 네 번째는 브라우저 표시 검사다.

지형 및 경로 검사는 통과했다. 모든 출발점에서 NPC 세 곳·문턱·진입점까지 엔진 경로가 존재한다. **정식 검사는 아래 NPC 정의가 없어 아직 실패한다.** 대사와 선물은 이 외형 작업에서 만들지 않았다.

- `entities/npc/temple_attendant.json`
- `entities/npc/guild_receptionist.json`
- `entities/npc/tavern_keeper.json`

등록 후 `check_town.py`로 다시 확인하고, from_layout과 town 참조 로딩 연결을 완료한 다음 실제 맵 채택 여부를 정한다. 현재 게임 실행과 진행 중인 원정은 바꾸지 않았다.
